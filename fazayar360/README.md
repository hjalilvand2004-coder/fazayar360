# فضایار۳۶۰ — مدیریت و بهینه‌سازی فضاهای آموزشی

زیرسیستم «فضایار۳۶۰» در زیست‌بوم **دانشجو۳۶۰**: مرجع عملیاتی شناخت، دسترس‌پذیری، رزرو و بهره‌برداری از فضاهای آموزشی دانشگاه.

> ارزش اصلی: **فضای مناسب، در زمان مناسب، با تجهیزات آماده و تخصیص قابل‌اعتماد.**

---

## ۱. استقرار سریع (روی سرور خودتان)

سرور هدف: `http://188.212.96.235:8095`

```bash
# روی سرور 188.212.96.235
unzip fazayar360.zip && cd fazayar360
docker compose up -d --build
# سپس: http://188.212.96.235:8095
```

- پورت `8095` مستقیماً روی میزبان منتشر می‌شود؛ نیازی به nginx نیست (FastAPI خودش SPA و API را سرو می‌کند).
- پیش از اجرای عملیاتی، مقدار `FAZAYAR_JWT_SECRET` را در `docker-compose.yml` (یا فایل `.env` کنار آن) عوض کنید.
- پایگاه داده PostgreSQL 16 به‌عنوان سرویس دوم بالا می‌آید و داده در volume `pgdata` می‌ماند.
- در اولین اجرا، اگر پایگاه داده خالی باشد، **داده نمونه** ساخته می‌شود (`FAZAYAR_SEED_ON_START=true`). برای استقرار واقعی این مقدار را `false` کنید.

## ۲. معماری

```
React 18 + TypeScript + Vite + Tailwind 4 (RTL، فونت Vazirmatn، تقویم شمسی با Intl)
        │
        ▼
FastAPI (Modular Monolith)
 ├── مدیریت فضا (ساختار سلسله‌مراتبی دانشگاه → پردیس → ساختمان → طبقه → فضا)
 ├── تجهیزات و آزمایشگاه (دارایی مستقل، استخر شمارشی، ظرفیت تجهیزاتی، ایمنی)
 ├── رزرو و تقویم (درخواست → بررسی → تأیید/رد → اجرا؛ سری تکرارشونده → رخداد تاریخ‌دار)
 ├── جست‌وجو و دستیار (متن فارسی → فیلتر؛ نتیجه فقط از داده واقعی)
 ├── تحلیل ظرفیت (نرخ اشغال، صندلی‌ـ‌ساعت، نقشه حرارتی، کیفیت داده، مرکز اقدام)
 ├── بهینه‌سازی (قواعد رتبه‌بندی قیدمحور؛ سناریو → پیشنهاد → تأیید انسانی → اعمال با اعتبارسنجی مجدد)
 ├── اتصال زیست‌بوم (رونوشت نسخه‌دار مراجع، رویداد ورودی تکرارپذیر، Outbox خروجی)
 └── دسترسی و ممیزی (JWT، نقش + حوزه سازمانی، audit_logs)
        │
        ├── PostgreSQL 16 (+ قید EXCLUDE USING gist برای جلوگیری قطعی از رزرو متعارض)
        └── Worker درون‌فرایندی برای اجرای بهینه‌سازی
```

**مطابق طرح، فضایار «تولیدکننده برنامه» نیست:** برنامه‌ریزی درسی و تخصیص استاد با زیرسیستم زمان‌بندی است؛ فضایار فقط تخصیص فضا را اعتبارسنجی و ثبت می‌کند و تقویم اشغال فضا **مرجع واحد** است.

## ۴. نقاط کلیدی پیاده‌سازی

### جلوگیری قطعی از رزرو متعارض
سه لایه:
1. بررسی تعارض در سرویس (بازه مؤثر شامل زمان آماده‌سازی و پاک‌سازی فضا)؛
2. قفل تراکنشی ردیف فضا (`SELECT … FOR UPDATE`) هنگام تأیید؛
3. قید دیتابیس `EXCLUDE USING gist (space_id WITH =, tstzrange(effective_start, effective_end) WITH &&) WHERE status='active'` — در صورت هم‌زمانی، فقط یکی commit می‌شود و دیگری **409** ساختاریافته می‌گیرد.

موجودی تجهیزات شمارشی (استخر لپ‌تاپ و…) با قفل تراکنشی ردیف استخر در لحظه تأیید کنترل می‌شود.

### ظرفیت مؤثر (عدد ثابت مبهم نیست)
`ظرفیت مؤثر = کمینه(ظرفیت چیدمان انتخابی، ظرفیت ایمن، ظرفیت تجهیزاتیِ تجهیزات الزامی)`
مثال: سالن سمینار در سخنرانی ۸۰، کارگاهی ۴۰، آزمون ۳۰ نفر؛ آزمایشگاه با ۱۲ ایستگاه دو نفره، ظرفیت تجهیزاتی ۲۴ نفر.

### دسترسی حوزه‌ای
دسترسی علاوه بر نقش، بر اساس دانشگاه/پردیس/ساختمان محدود می‌شود؛ مسئول آزمایشگاه نمونه فقط ساختمان خودش را می‌بیند و می‌تواند تغییر دهد.

### دستیار «فضای مناسب پیدا کن»
متن فارسی («برای سه‌شنبه ساعت ۱۰، یک کلاس برای ۳۲ نفر با نمایشگر») با قواعد قطعی به فیلتر تبدیل می‌شود؛ نتیجه فقط از داده واقعی است و **رزرو نهایی با تأیید کاربر و اعتبارسنجی قطعی ثبت می‌شود — LLM مرجع آزادبودن فضا نیست.**

### QR کنار در و صفحه عمومی
`/#/public/spaces/{slug}` بدون احراز هویت: شناسنامه، برنامه امروز (بدون نام افراد)، تجهیزات، راه ارتباط با مسئول و فرم ثبت گزارش خرابی. گزارش‌ها در مرکز انسداد به‌صورت «نیازمند بررسی» ثبت و توسط مسئول ساختمان به انسداد فعال تبدیل می‌شوند.

### امنیت و قابلیت اعتماد
- احراز هویت JWT (نقطه اتصال OIDC سرویس هویت زیست‌بوم در `core/security` جایگزین‌شدنی است)
- کنترل دسترسی فقط در بک‌اند؛ خطاهای ساختاریافته + `X-Request-ID` (شناسه رهگیری)
- `Idempotency-Key` برای ثبت درخواست حساس؛ پردازش تکرارپذیر رویدادهای ورودی با `external_event_id`
- الگوی Outbox برای رویدادهای خروجی (`booking.confirmed`, `space.blocked`, …)
- ممیزی کامل تغییرات حساس در `audit_logs`؛ کنترل نسخه رکورد (optimistic locking) در PATCH فضا
- محدودسازی نرخ، محدودسازی نوع/حجم فایل بارگذاری، حذف تاریخچه‌محور (بازنشستگی فضا به‌جای حذف)

### شاخص‌های تحلیل
نرخ اشغال زمانی برنامه‌ریزی‌شده، نرخ استفاده واقعی، تناسب ظرفیت، صندلی‌ـ‌ساعت، نرخ لغو، عدم استفاده از رزرو، زمان ازکارافتادگی، نقشه حرارتی روز×ساعت، کیفیت داده و **مرکز اقدام** (هر هشدار دکمه اقدام دارد). اگر داده حضور واقعی نباشد، شاخص صریحاً «برآورد مبتنی بر ثبت‌نام» برچسب می‌خورد.

## ۵. API (پیشوند `/api/v1`)

مستندات تعاملی: `/api/v1/docs` (OpenAPI)

مسیرهای اصلی طبق طرح: `GET/POST /spaces`، `GET/PATCH /spaces/{id}`، `GET /spaces/{id}/availability|calendar`،
`POST /availability/search`، `POST /booking-requests` و `…/approve|reject|cancel`، `POST /booking-requests/conflict-preview`،
`POST /booking-requests/occurrences/{id}/move`، `POST /maintenance-blocks` (+ resolve و گزارش خرابی)،
`POST /usage-observations`، `GET /analytics/utilization|heatmap|quality|action-center`،
`POST /optimization-runs` و `GET /{id}` و `POST /{id}/apply`، `GET /integrations/references|events` و `POST /integrations/events`،
`GET /admin/audit-logs`، مسیرهای عمومی `/public/spaces/{slug}`.

## ۸. نسخه پرتیبل (بدون نیاز به پایتون/پای‌چارم/PostgreSQL/Docker)

از دارایی‌های ریلیز، فایل `fazayar360-portable-linux-x64-v1.0.0.tar.gz` را بگیرید:

```bash
tar xzf fazayar360-portable-linux-x64-v1.0.0.tar.gz
cd fazayar360-portable && ./start.sh
# → http://localhost:8095    (کاربر مدیر: admin / Faza360!)
```

این بسته شامل **مفسر مستقل Python 3.12**، همه وابستگی‌ها و **PostgreSQL توکار (pgserver)** است؛
روی لینوکس x86_64 (glibc ≥ 2.17) بدون هیچ نصب پیش‌نیازی اجرا می‌شود. داده‌ها در پوشه‌ی `data/`
باقی می‌مانند و با کپی کل پوشه قابل انتقال است. تغییر پورت: `FAZAYAR_PORT=8090 ./start.sh`
در نبود افزونه btree_gist، سامانه با هشدار اجرا می‌شود و جلوگیری از تعارض به قفل تراکنشی سپرده می‌شود.
